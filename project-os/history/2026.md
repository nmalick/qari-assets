### 2026-06-28 — SHIPPED — README added; auto-release cuts `qari-assets-7` on a doc-only push
A 20-line README describing repo layout, asset variants, helper scripts and the release model
landed directly on main. It is the first push to main after the auto-release workflow went in,
and it fired the pipeline: annotated tag `qari-assets-7` was cut against the same commit
(tagger date 2026-06-29 UTC). A documentation-only commit therefore burned a release number —
precisely the case the workflow's commented-out path filter was written to suppress.
**Verified**: commit 4f8972d; tag qari-assets-7; .github/workflows/auto-release.yml:16-25

### 2026-05-27 — DECISION — Auto-tag + GitHub Release on every push to main (`qari-assets-N`)
Replaced manual tagging with a GitHub Actions workflow that, on every push to `main` (direct or
merged PR), computes the next release number and cuts an annotated tag plus a matching Release
with auto-generated notes. Rationale recorded in the commit: the consuming Flutter client pins
its asset base URL to a specific release tag at build time, so every main update needs a stable
anchor without anyone touching the Releases page by hand. Bump strategy is max-existing-N + 1
with numeric (not lexicographic) sort, so gaps in the sequence are tolerated. Safety rails:
a serialized `concurrency` group with `cancel-in-progress: false` (half-released tags are worse
than late ones), a `[skip release]` commit-message opt-out, and `workflow_dispatch` for backfills.
The workflow deliberately does **not** regenerate `manifest.json` — the manifest is still rebuilt
by hand with `_build_manifest.py --ref qari-assets-N` when assets actually change.
**Verified**: commit 791ee7c; commit a031010; .github/workflows/auto-release.yml:33-35;
.github/workflows/auto-release.yml:46; .github/workflows/auto-release.yml:62-71

### 2026-05-27 — SHIPPED — Three new mushaf variants (DK V2, V1+Tajweed, Nastaleeq) + schema v4
Expanded the catalogue from 2 variants to 5: the existing per-page `v4-tajweed` and `v1-madina`
were joined by `v2-dk` (Digital Khatt V2), `v1-madina-tajweed` (Digital Khatt V1 + Tajweed) and
`nastaleeq` (KFGQPC Nastaleeq). The three new ones are a structurally different shape — one
OTF/TTF per variant driven by Unicode shaping, sharing a single `qpc-hafs.db` (83,668 words)
rather than 604 PUA-encoded per-page fonts. `_VARIANTS` gained a `mode` field (`per_page` vs
`single_font`) and a `_build_single_font_variant()` path that emits a `singleFont` block with an
empty `fonts: []` array. Schema bumped 3 → 4 and `releaseTag` 1.2.0 → 1.4.0 (1.3.0 was skipped).
Assets sourced from QUL: DK V2, DK V1, Nastaleeq and the KFGQPC Hafs word-by-word SQLite.
**Verified**: commit fdb32da; commit a0dc7a1; manifest.json:2; _build_manifest.py:71-77;
_build_manifest.py:78

### 2026-05-27 — FIX — `_parse_family()` decoded Unicode-platform name records as mac-roman
Latent bug in the manifest builder, fixed inside the same change: OpenType `name` records with
`platformID=0` (Unicode) are UTF-16BE, not mac-roman. Any font whose first nameID-1 record was
platform 0 produced a garbled family name in the manifest. Surfaced when the first OTF-format
variants were added.
**Verified**: commit fdb32da

### 2026-05-21 — REFACTOR — Builder parameterized: `--ref` / `--release-tag` replace hardcoded values
`_build_manifest.py` previously hardcoded the manifest's `baseUrl` ref and `releaseTag`, so
cutting a release meant editing the script and re-committing. Added `--ref` (also read from
`$QARI_ASSETS_REF`, default `main`) and `--release-tag` (also `$QARI_ASSETS_RELEASE_TAG`).
The commit records the resulting cosmetic defect it was fixing: the manifest shipped at
`qari-assets-5` still advertised a `qari-assets-4/` base URL, harmless because the consuming
Flutter client overrides the field, but misleading to anyone reading the manifest to debug.
**Verified**: commit 0a367e7; commit 2478555; _build_manifest.py:68-69

### 2026-05-21 — FIX — V1 rendering fed V4 PUA codepoints; per-variant words DB + schema v3
V1 pages were rendering fragmented/garbled text because V4-encoded PUA codepoints
(U+FC41..U+FDFD, from `qpc-v4.db`) were being resolved against V1 `QCF_P{NNN}` fonts, which
expect a different PUA scheme (U+FB00..U+FBFF). Fix: extract and commit `qpc-v1.db`
(same schema as `qpc-v4.db`, 83,668 rows, shared word-ID space) and bump the manifest to
schemaVersion 3 with a per-variant `wordsDb` block — `v1-madina` → `qpc-v1.db`,
`v4-tajweed` → `qpc-v4.db`. The top-level `wordsDb` was deliberately retained pointing at
`qpc-v4.db` so schemaVersion-2 clients keep parsing with unchanged (still-wrong-for-V1)
behavior rather than breaking. The V4 words-DB SHA-256 was left unchanged so existing client
disk caches stayed valid. Same change deleted every remaining zip in the repo.
**Verified**: commit bfc84c3; commit c0d6d74

### 2026-05-21 — SHIPPED — V1 word-codepoint DB uploaded; tagged `qari-assets-4`
`qpc-v1-glyph-codes-wbw.db.zip` uploaded straight to main via the GitHub web UI (no PR), and
tagged `qari-assets-4`. It is the input the schema-v3 fix above extracts `qpc-v1.db` from, and
the archive itself was deleted in that same follow-up commit.
**Verified**: commit 744521e; tag qari-assets-4

### 2026-05-21 — REFACTOR — 54 MB font archive dropped; two builders consolidated into one
Deleted `QPC V1 Font.ttf.bz2` (54 MB), redundant once the 604 V1 TTFs were extracted under
`fonts/v1/`. Renamed `_build_manifest_v2.py` → `_build_manifest.py` and rewrote it to be
self-contained: it walks `fonts/<variantId>/` on disk and recomputes SHA-256 and sizes fresh,
so adding a variant becomes "drop fonts in a subdir, append to `_VARIANTS`". Regenerating the
manifest also fixed a pre-existing bug where V4's `totalSizeBytes` was inflated by exactly the
size of `qpc-v4.db` (169,423,944 → 166,986,824) and dropped two debug-only fields.
**Verified**: commit 37ef690; commit 9ff1baf

### 2026-05-21 — SHIPPED — 604 V1 Madina per-page fonts + multi-variant schema v2
Staged 604 V1 Madina (1405H) per-page TTFs under `fonts/v1/` and replaced the single-variant
manifest with a schemaVersion 2 multi-variant document holding both `v1-madina` and
`v4-tajweed`. Each variant carries its own `fontDir`, `familyPattern`, `tajweedColored` flag and
per-page font metadata; V4 entries were preserved verbatim and the shared words DB was promoted
to the top level. This is the commit that turned a one-mushaf repo into a variant catalogue.
The source archive arrived one commit earlier as `QPC V1 Font.ttf.bz2`.
**Verified**: commit 998b7e8; commit c9209b7; commit cbdfa90

### 2026-05-16 — SHIPPED — LICENSE.txt (KFGQPC) + per-font embedded restriction recorded
Added the KFGQPC electronic end-user license verbatim and registered it in the manifest with
sha256 and size. The commit body records a material finding that the license file alone does not
convey: every `fonts/v4-tajweed/p*.ttf` embeds a *more restrictive* clause in its `name` table
(id 10) limiting the tajweed-color variant to charitable use, with printing and publishing
barred without prior permission. That embedded clause controls for those fonts, and any
commercial monetization of the tajweed view needs clearing with KFGQPC first.
**Verified**: commit f614411; commit a68ae3c; tag qari-assets

### 2026-05-16 — DROPPED — `pages.zip` and `surah-name-v2.ttf` removed as redundant/unused
`pages.zip` was a DOCX-format duplicate of `qpc-v4.db` — the same 83,668 word codepoints in 604
Word files instead of a queryable SQLite; `qpc-v4.db` was declared canonical. `surah-name-v2.ttf`
carried V2-style surah headers unused by the V4 pipeline; `surah-name-v4.ttf` was kept.
**Verified**: commit 4de5d8c

### 2026-05-16 — SHIPPED — `qpc-v4.db` word-codepoint mapping completes the V4 pipeline
Committed the V4 word-by-word resource (`words(id, location, surah, ayah, word, text)`,
83,668 rows, Arabic Presentation Forms codepoints) as a raw `.db`, dropping its zip. The commit
records an end-to-end verification: word IDs 1..83668 cover every layout reference with zero
misses, page-100 codepoints all resolve in that page's font cmap, and a joined render of page 1
matched the DOCX reference exactly. This closed the three-stage chain — layout DB → word text →
per-page font glyph.
**Verified**: commit 186b5fe

### 2026-05-16 — SHIPPED — 604 QCF V4 tajweed-color page fonts + manifest schema v1
Fetched all 604 per-page fonts of KFGQPC's official V4 set (1441H print, family
`QCF4{NNN}_COLOR`, COLR/CPAL tajweed color tables) from the QUL CDN — 159.3 MB — via a purpose-
built parallel fetcher that verifies sfnt magic bytes and retries transient failures. Introduced
`manifest.json` at schemaVersion 1: a single-variant document indexing filename, family, sha256
and sizeBytes per page. The commit explicitly lists what was still missing at that point: the
per-word codepoint mapping (gated behind QUL sign-in) and the license file.
**Verified**: commit ba9dd9e; _fetch_v4_tajweed.py:15

### 2026-05-16 — REFACTOR — Repo cleaned to a serve-raw-artifacts convention
Removed a byte-identical duplicate DB archive, a JSON twin of the same DB (3× size, no indexes),
and two archives belonging bundled inside the consuming Flutter client rather than served from
this CDN. Unzipped the five surah-header / common-glyph fonts to raw `.ttf` so they can be served
directly at the release-download URL. This established the convention the repo has kept since:
raw artifacts only, no archives.
**Verified**: commit b51d07b

### 2026-05-16 — SHIPPED — Initial asset uploads seed the repository
Three web-UI uploads (`Add files via upload`) seeded the repo with zipped fonts, word-by-word
DBs and layout DBs — nine archives, then `pages.zip`, then `qpc-v4.db.zip`. Every one of these
was either unzipped or deleted within the same day.
**Verified**: commit 407d8ae; commit 68e0200; commit 4f5cbe6
